요청: $ARGUMENTS

아래 5단계를 **순서대로** 진행한다. 각 단계 끝에서 반드시 멈추고 사용자의 "다음"을 기다린다. 단계를 건너뛰거나 합치지 않는다.
CLAUDE.md 작업 규칙(직접 수정 금지, 스니펫 제공, 커밋은 사용자)이 모든 단계에 적용된다.

## 1단계: 기획
- 해결하려는 문제, 완료 조건(Acceptance Criteria), 범위 밖인 것을 3~5줄로 정리한다.
- 불명확한 점(엣지 케이스, 에러 처리, 동시성, 기존 API 호환)을 질문 목록으로 제시한다.
- ⏸ 사용자 답변과 승인 대기.

## 2단계: 로직 설계
- 관련 파일을 읽고(@docs/architecture.md 포함) 영향받는 파일 목록을 제시한다.
- 구현안 2개를 비교한다: 각 안의 변경 파일, 트랜잭션 경계, 외부 호출 시점(AfterCommit 필요 여부), 장단점.
- 추천안과 이유를 쓴다.
- ⏸ 사용자가 안을 선택할 때까지 대기.

## 3단계: 테스트 먼저 설계
- 구현 전에 테스트 케이스 목록을 만든다: 정상 / 경계값 / 실패(외부 API 실패, 동시성, 권한).
- 테스트 코드 스니펫을 CLAUDE.md 테스트 컨벤션으로 작성한다.
- ⏸ 사용자 승인 대기.

## 4단계: 구현
- 선택된 안대로 파일별 스니펫을 제공한다. 각 스니펫에 "왜 이렇게 했는지" 1~2줄.
- 사용자가 적용 후 실행할 명령: `./gradlew compileJava` → 해당 테스트 `./gradlew test --tests "..."`.
- ⏸ 사용자가 테스트 결과를 붙여넣을 때까지 대기. 실패하면 원인 분석 후 4단계를 반복한다.

## 5단계: 셀프 리뷰
- `psik-backend-reviewer` 에이전트로 변경분(마지막 커밋 이후 변경은 `git diff HEAD`, 이미 커밋했다면 `git diff HEAD~1`)을 리뷰한다.
- 1단계 완료 조건을 하나씩 체크해 충족/미충족을 표로 보고한다.
- 새로 생긴 기술 부채가 있으면 `docs/architecture.md`의 "알려진 기술 부채"에 추가할 문구를 제안한다.
- 커밋 메시지 초안(`type: 설명`)을 제공한다. 커밋은 사용자가 한다.
